# F03 frozen movie/chunk contract and local verification

The coordinator approved and froze this additive contract. The isolated local implementation is verified below; online movie enablement remains off pending coordinator acceptance. The existing 60-second production/episode authoring limits remain. Only the coordinator edits schema/generated files, deploys, or performs online database tests. No provider purchase, new service, or AI-generated executable code is part of movie assembly.

## Existing authority and verified constraints

- `convex/episodes.ts`: each episode owns a distinct production; episode creation is 4–60 seconds, at most 500 numbered episodes per project. Episode story states are separate retained versions.
- `convex/productions.ts`: an approved production plan is at most 60 seconds/200 shots. This remains the unit for creative planning and generation.
- `convex/assembly.ts`: locked timeline/current approved production → canonical manifest v4/v5; selected shots/scenes pack picture windows and rebase/crop independent audio and captions; ambiguous partial transitions/audio fades fail explicitly. Stored manifests include exact source/shot/timeline bindings, source checksums and frame timing, with a 900 KiB cap. Source checksums currently include a noncryptographic legacy summary; movie authority must additionally SHA-256 the canonical stored manifest.
- `convex/renderJobs.ts`: canonical asset/take approval, exact lease, dispatch, callback and retained completion authority already exist. Render jobs/manifests/exports require a production ID. Existing completed artifacts can be reused after reauthorization and storage/checksum verification. The current dispatch caps source rows/items at 200.
- `convex/reviewExport.ts`: production reviews, exports and share links bind one exact manifest/timeline/export. They cannot truthfully represent a cross-production movie by assigning it to the first episode.
- Renderer: one serial render queue and a shared render/probe/analysis gate; persistent completion outbox; normalized frame/sample timing; default render cap 18,000 frames, command cap 900 seconds, output cap 2 GB. `manifest.ts` has a broader reader cap, which is not authorization to submit a monolithic long render. No cap/concurrency/host CPU/RAM increase is proposed.

## Chosen architecture

A movie version is an immutable ordered set of component references. Each component points to one already locked, approved canonical manifest v5 from a single production/episode, at most 60 seconds and within existing source limits. Chapters are contiguous groups of these component occurrences. The same source may appear deliberately more than once; occurrence IDs disambiguate selection and review.

Movie references are fixed at creation. Asynchronous validation resolves one component per transaction, records a source digest/output/map once, and can only change validation bookkeeping thereafter. A version becomes READY only when all components pass and its ordered digest/duration are sealed. Invalid content is repaired by creating a new version; no in-place reorder, source substitution or edit of an approved version. Retained source versions remain exact; no following a production's mutable current pointer. Retained older versions require explicit confirmation at creation. Episode story-state/bible IDs are recorded when present; continuity warnings require explicit movie review, never a fabricated consistency guarantee.

READY means validation only. Add project-owned resource types `movieVersion`, `movieReview`, and `movieExport` to the existing `resourceStates.ts` type/ownership resolver and supported project-owned approval allowlist. `movieVersion` resolves through its movie/project; review/export resolve through their exact version/project. Production IDs remain absent for these resources. Approval/locking/client review decisions use canonical `resourceStates`/`approvals`; no new decision table or second approval authority. Owner/editor must submit, approve and lock a READY movie version before movie rendering. A movie review decision uses its canonical resource state, not a duplicate status field on `movieReviews`. Review-purpose artifacts can be rendered from that locked assembly; delivery promotes/reuses an exact approved review artifact without rendering again. Lock/approval cannot authorize an INVALID or still-VALIDATING version.

Component renders reuse the existing canonical `renderJobs` pipeline and completed verified exports. The only new heavy operation is a movie-owned bounded merge, using the same isolated worker, queue/gate, transfer primitives, persistent outbox, signatures and exact attempt/lease/receipt rules. The movie itself is not represented as a fake production, nor as a giant embedded RenderManifest.

## Proposed APIs and frozen wire shapes

False-by-default flags: `FINALFRAME_MOVIE_ENABLED` (authoring/export/review writes and worker route), `FINALFRAME_MOVIE_WORKER_ENABLED` (scheduled merge orchestration). Retained queries stay readable when flags are disabled. Existing render/manifest v5 flags remain separate prerequisites, not silently enabled.

Proposed shared pure planner types are `MovieCompositionHeader` (`kind:'finalframe.movie-composition'`, `version:1`, `projectId`, `movieVersionId`, `output`, `durationInFrames`, `componentCount`, `contentHash`) and paged `MovieComponentReference` rows (`componentId`, `orderIndex`, chapter identity, exact episode/production/productionVersion/timeline/timelineVersion references, `manifestId`, `manifestVersion:5`, `sourceManifestSha256`, `startFrame`, `durationInFrames`, bounded `sourceMap`). IDs are opaque strings in pure renderer contracts and exact `v.id` types in Convex APIs. The header contains no embedded graph or component manifests. `MovieExportPlan` contains `{movieVersionId,contentHash,selection,output,durationInFrames,planHash,parts:[{componentId,sourceStartFrame,durationInFrames,outputStartFrame,sourceManifestSha256}]}` and is persisted as separate part rows; the worker resolves verified chunk artifacts, not original AI/generation requests.

- `movies.create({projectId,title,idempotencyKey})`; `movies.createVersion({movieId,parentVersionId?,output,confirmedRetainedVersions,components:[exact reference/chapter fields above],idempotencyKey})`. Creation key scope includes project/user/parent/full ordered body; changed-body replay denies after fresh authorization. `movies.listVersions/getVersion/components` use bounded pagination. Creation schedules one-component validation steps, never loads 128 near-1MiB manifests in one mutation.
- `movieExports.preview({movieVersionId,selection})` produces an immutable deterministic frame/range plan and hash; `request({...same,purpose,approvedReviewId?,expectedPlanHash,idempotencyKey})` persists parts and schedules orchestration. DELIVERY requires the exact canonical approved movie review; REVIEW permits initial review output from the locked movie assembly. `retry({movieExportId})` retains verified parts and only resumes missing/failed/reconciled work; `cancel` stops future claims, does not cancel shared component renders needed by other exports, and keeps completed artifacts.
- Component selection is occurrence-qualified. SCENES/SHOTS require `{componentId,sceneId}` or `{componentId,shotVersionId}`, so repeated source shots/episodes are not ambiguous. Selected parts pack in movie order; CHAPTERS refer only to contiguous declared groups. Ambiguous partial non-cut transitions/audio envelopes require a dedicated approved selection manifest rather than dropping neighboring pictures or changing sound. Selected outputs crop/rebase captions and map timestamps from the same exact frame windows.
- `movieReviews.request({movieExportId,idempotencyKey})`, comment/approve/revise/share-link operations bind exact movie version/export/plan hash. Review timestamps use integer `movieFrame`, `0 <= frame < durationInFrames`; the server derives component-local frame and all source contributors from frozen maps. Public shared access rechecks project restrictions, token/expiry/revocation, exact completed stored artifact and exact review identity as existing production reviews do.

New authenticated worker route: `POST /movie/merge`. Header is the existing worker shared secret. Request:

```
{version:1,kind:'finalframe.movie-merge',mediaAbi,jobId,projectId,movieVersionId,movieExportId,
 planHash,idempotencyKey,attempt,leaseId,callbackUrl,heartbeatUrl,storageUploadUrl,
 output:{width,height,fps,durationInFrames,codec:'h264',audioSampleRate:48000,audioChannels:2},
 parts:[{partId,componentId,orderIndex,sourceManifestId,sourceManifestSha256,
         renderJobId,storageId,checksum,byteSize,url,
         sourceDurationInFrames,sourceStartFrame,durationInFrames,outputStartFrame}]}
```

Fresh canonical URLs are resolved by the coordinator immediately before dispatch from exact READY part/storage IDs. Worker verifies exact byte count/SHA before using a part; URL strings are not source authority. Payload size <=384 KiB, parts <=256, redirects denied, origins pinned, downloads streamed. No project/member browser chooses raw URLs or upload destinations.

New pinned callbacks `/renderer/movie-callback` and `/renderer/movie-heartbeat`. Reuse v1 `render.completed|render.failed` envelope with `jobId` typed to `movieMergeJobs` only in the new handler. Payload includes exact `{movieVersionId,movieExportId,planHash,leaseId,storageId,checksum,durationInFrames,verification}`. Existing `/renderer/callback` remains restricted to `renderJobs`; do not broaden it into accepting arbitrary table IDs. Heartbeat carries the same exact signed lease authority, stage/progress and 30s/10s cadence, with 425 before acceptance. Transfer/outbox can use a clearly named deterministic movie artifact identity instead of claiming a production manifest ID. Same exact-body HMAC, fresh delivery signature, 2h attempt reconciliation and 24h exact-receipt no-op replay policy apply.

## Merge execution and bounds

- Maximum 1,800 seconds, 128 components, 256 selected export parts, supported FPS 24/25/30/50/60, one declared width/height and H264 delivery preset. Each component remains <=60 seconds and existing 200-source/item worker bounds. Different dimensions/FPS/codecs/timebase or incompatible H264 configuration fail preflight; no implicit quality conversion or giant fallback re-render.
- Same host render queue and shared media gate serialize merge/render/probe/analysis. Merge admission returns 429 while incompatible heavy work owns capacity. Durable dispatch additionally checks live ordinary render and movie merge leases; no concurrency/CPU/RAM increase. Busy delivery retries the same frozen attempt and does not discard completed parts.
- Reuse a completed component only after checking same project, exact source manifest SHA/version, output signature/renderer ABI, complete job/export identity, current source permissions/approval/rights, actual storage MIME/bytes/SHA and verification. Extract a single canonical component-render factory shared with existing `renderJobs` creation/dispatch; avoid a separate creative submission path. The cache key is a SHA-256 digest of project + manifest identity/hash + output signature + renderer ABI, with existing <=200-character idempotency keys. There is no `generationJobs` call in this path.
- First safe vertical slice uses whole completed component ranges. Frame-exact selected range extraction is enabled only after boundary/audio/caption tests; no keyframe-rounded cuts. Manifest-bound non-cut overlaps are kept within a component. Cross-component transitions are explicit CUT in this first contract; existing v5 transitions remain fully rendered inside components.
- For subsequent SCENES/SHOTS range exports, a cropped part is decoded and re-encoded as a bounded <=60s derived part using exact `trim=start_frame/end_frame` and canonical audio sample windows, then verified before joining. Do not use input seeking plus video stream-copy as a claim of frame-exact cropping. Completed full component media remains retained; no provider/creative rerender is needed. The derived output must match the canonical join stream signature; otherwise fail clearly rather than silently transcoding the whole movie.
- Download verified component artifacts with total input <=2 GB. Verify canonical H264 stream configuration before video stream-copy concatenation. Do not stream-copy independent AAC packets across chunk boundaries: decode each chunk's audio to its exact canonical frame-derived PCM sample window, pad silent chunks only where the movie has audio, append bounded PCM on disk, and encode AAC once for the final movie. Supported FPS divides 48 kHz exactly. This removes per-chunk encoder priming/padding accumulation without stretching or changing content timing. Fully silent movies can remain without an audio track.
- Process one part at a time for PCM, with bounded buffers; no 30-minute uncompressed media in RAM and no shell interpolation. Download/decode/mux share an overall <=900-second heavy-work deadline, never a fresh 900 seconds per part. Final video mux is bounded by exact total frames/time, output <=2 GB, stream/frame-count probe and checksum. Input + output + <=346 MB stereo16 PCM require a measured free-space admission check with an explicit scratch ceiling/reserve; proposed ceiling 5 GB plus a 1 GB untouched filesystem reserve. Use a private directory on the existing persistent worker volume, not a RAM-backed `/tmp` for GB work. This is a disk admission limit, not a blind volume enlargement. Keep the existing 1 CPU/2 GiB service limits. If actual host capacity cannot support it, keep the feature flag false.
- Accepted merge expiry enters reconciliation/NEEDS_ATTENTION rather than automatically re-merging an unknown successful result. Successful upload/callback outage replays the exact saved artifact/receipt. Retained completed chunks survive cancellation, retry, callback loss, server restart and later versions referencing the same immutable source. Storage cleanup requires explicit retention rules and cannot delete artifacts referenced by another version/export.
- Caption sidecars derive from component canonical cues and selected frame windows. Keep track/language/occurrence identities truthful; do not merge overlapping same-language tracks into ambiguous plain SRT. Bound whole-movie cue/text totals before download generation, stream/paginate source loading, and reject excess rather than truncate.

A 2 GB application ceiling therefore does not certify that a 2 GB artifact can upload from this host. No plan purchase or paid storage expansion is authorized here. Current transaction/read/document limits also favor one-component validation steps and bounded pagination rather than loading the entire graph. [Official limits](https://docs.convex.dev/production/state/limits)

A job reserves its calculated work budget and retains at least 1 GB of free space; existing artifacts are not deleted to satisfy admission.

Storage download URLs are bearer capabilities, not automatically expiring permission checks. Revoking a review link prevents future application access but does not revoke a previously copied media URL. HTTP-action responses are limited to 100 MiB, so proxying a larger final movie through a Convex HTTP action is not an assumed solution. Retain the application's explicit bearer-download security model; do not promise stronger media-URL revocation without a separately approved design. ## Frozen authority and ABI additions

Each validated source map records `assetStorageId`, the raw opaque `assetChecksum`, and the raw canonical `assetStorageChecksum`, all derived from actual owned asset/Storage records. Raw Storage SHA lineage remains unchanged; only comparisons and certified worker digests normalize strict canonical base64/hex using `normalizeSha256`. Optional `fadeInFrames`/`fadeOutFrames` make partial audio-envelope selections explicit failures. Public source/status responses omit storage proof fields.

Across the composition, enforce at most 1,024 unique authority objects, 2 MiB serialized aggregate source maps, and 4 MiB loaded authority metadata. Metadata and object budget violations fail closed. Validation remains one full component manifest per transaction. The first merge dispatch **and every unaccepted retry**, final DELIVERY promotion, download, sidecar access, and member/shared review access atomically recheck compact current ownership, canonical resource states, asset rights and exact Storage snapshots. They do not load every original near-1-MiB manifest. Shared membership resolution honors canonical tombstones, the verified primary user identity and legacy linked-user matching. Continuity-bible mirrored `APPROVED` never overrides a revised canonical resource state.

`FINALFRAME_MOVIE_MEDIA_ABI` must be configured before new component/merge work. `renderJobs.movieMediaAbi`, `movieExports.mediaAbi` and `movieMergeJobs.mediaAbi` freeze it. Component cache identity includes this value; completed chunks require the actual signed worker version in `renderJobs.providerJobId`, not the generic manifest renderer label. A queued component dispatch refuses an obsolete frozen ABI. The merge wire includes `mediaAbi`; the worker compares it to its actual `RENDERER_VERSION` before accepting. The signed movie callback's `rendererVersion` must equal the frozen accepted ABI.

After acceptance, the exact accepted plan/ABI/lease may record its output privately through the existing bounded reconciliation window despite later actor/source revocation or configuration changes. It never resubmits accepted work. Current source/ABI checks still guard every new URL/review/share/promotion. Already shared bearer URLs cannot be revoked without deleting their stored files; application link revocation blocks future application access.

## Storage and rollout gates

Private worker admission checks a private directory on a persistent filesystem, output/work on the same filesystem, <=5 GB calculated scratch including a32 MiB allowance for one transient PCM piece/mux packet staging, and >=1 GB remaining measured free space.
